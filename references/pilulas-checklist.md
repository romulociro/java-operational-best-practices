# Checklist Pílulas de Java (Wandi)
Fonte: Wanderlei Souza — https://www.linkedin.com/in/wandi/
Carregar este arquivo quando precisar da regra numerada completa ou ao aplicar o checklist por tema.
- **#13 Nunca bloquear chamadas em código assíncrono:** Esse padrão parece inofensivo, mas quebra completamente a ideia de programação assíncrona: o código fica travado esperando o resultado, gerando thread starvation e reduzindo drasticamente a escalabilidade. A boa prática é encadear operações assíncronas em vez de bloquear.
- **#14 Sempre leia as letras miúdas dos Collectors:** Um detalhe pouco percebido ao usar Collectors.toMap() é que, se houver chaves duplicadas, seu código falha em tempo de execução com IllegalStateException. No print abaixo, um e-mail repetido quebra tudo - e logo o seu telefone irá tocar.
- **#15 Uma alternativa aos construtores são os métodos de fábrica estáticos:** Construtores com muitos parâmetros soltos tornam o código difícil de ler e geram confusão ao criar objetos. Uma alternativa é usar métodos de fábrica estáticos, que trazem nomes claros e reduzem a dependência de documentação (nomes significativos tornam o código autoexplicativo).
- **#16 Testes parametrizados de classe no novo JUnit 6:** O JUnit 6 foi lançado em 30 de setembro e uma das novidades mais úteis é o @ParameterizedClass. Antes, só era possível parametrizar métodos individuais com @ParameterizedTest, o que obrigava a repetir a mesma configuração em cada teste ou até duplicar classes quando se queria rodar toda a suíte em cenários diferentes.
- **#17 O erro invisível nos Builders: mutabilidade disfarçada de elegância:** Muitos builders em Java parecem corretos, mas escondem um problema silencioso: o vazamento de mutabilidade. Quando o objeto construído guarda uma referência direta para a lista usada dentro do builder, qualquer modificação fora dele pode alterar o estado interno do objeto “imutável”.
- **#18 — Builders com ordem guiada e instâncias realmente imutáveis (aka Builders parte 2):** Outro problema frequente em Builders é o "telescoping builder": trocar um construtor gigante por trocentos setters sem sentido. Um bom builder define o essencial no ponto de entrada e, se a sequência importa, guia a ordem de chamadas por estágios.
- **#19 Builders e Factory Methods: a criação deve falar por si e outros detalhes finais (Aka Builders, Parte 3):** Builders tornam APIs fluentes, bem feitos simplificam; mal usados, camuflam bugs. Fechando a série de Builders com mais alguns detalhes que fazem diferença em produção.
- **#20 Sequenced Collections: o update que arrumou o caos (e criou um novo "bug" comum nas reviews):** Antes de Sequenced Collections, cada coleção lidava com ordem de forma diferente e sem interface comum: List permitia add(0, x) para inserir no início (ineficiente em ArrayList), LinkedHashMap não tinha getFirst nem reversed(), e Set ordenado exigia NavigableSet.descendingSet() (só disponível em TreeSet). Parecia que ninguém se falava no design da linguagem.
- **#21 Pare de espalhar static final sem tipos semânticos - use enum:** Constantes não expressam intenção. Tipos semânticos contam histórias Ainda é comum ver sistemas cheios de static final usados para representar estados, papéis ou tipos.
- **#24 Todo switch com enum parece inofensivo… até o próximo deploy:** Para fechar a série sobre enums (volta lá na pílula #21), dois erros finais: (1) usar switch com default e (2) espalhar switch pelo código para “interpretar” o enum. Parecem detalhes, mas os dois viram dívida séria de manutenção.
- **#25 No Brasileirão, na dúvida, chama o VAR. No Java, é o contrário.:** Eu gosto de usar var no Java. Ele deixa o código mais limpo e reduz o ruído visual.
- **#27 Singleton, o padrão que o GoF consagrou, mas nasceu quebrado:** Quando o Gang of Four (GoF) lançou o Design Patterns em 1994, o Singleton era simples e funcionava para aplicações single-threaded. Com a adoção de multithreading, surgiu o problema: duas threads podiam criar instâncias diferentes.
- **#28 Como o Spring cria Singletons (e por que não é o Singleton do GoF):** Depois da Pílula 27, muita gente perguntou como o Spring lida com singletons e se ele usa Double Checked Locking, volatile ou algum padrão clássico. A resposta é interessante porque o Spring resolve o problema de outra forma.
- **#30 Por que java.lang.Math não tem construtor público? (e como aplicar isso nas suas classes):** Nem toda classe representa um objeto do domínio. Algumas existem exclusivamente como agrupamentos lógicos de operações estáticas, sem estado, identidade ou comportamento de instância.
- **#31 Por que seu código é impossível de testar (e como Hollywood resolve isso):** Você escreve o teste, roda, e ele dispara um email de verdade. Ou tenta simular uma falha de rede, mas não consegue.
- **#32 Duas coisas são infinitas: o universo e o sofrimento do GC com sua lista…:** Nenhuma estrutura em memória deve crescer sem limite; use fila limitada (poll além do teto) ou limpeza agendada.
- **#33 Por que seu sistema Java trava depois de 100 requisições? Pode ser vazamento de recursos:** Muitos devs pensam que basta implementar AutoCloseable e o recurso se fecha sozinho em algum momento. Isso é falso.
- **#34 Abstrações vs implementações, onde usar cada uma:** Quando você usa tipos concretos (ArrayList, HashSet, TreeSet) em vez de suas interfaces (List, Collection, Set), está limitando a flexibilidade do seu código. Em um serviço de precificação que precisa receber pedidos para recalcular margens, exigir ArrayList ou HashMap obriga todos os chamadores a seguir uma implementação específica.
- **#35 O verdadeiro monstro da engenharia na Netflix não era o Demogorgon, era o Thread Pinning do Java 21:** Quando o Java 21 chegou, muitos desenvolvedores adotaram virtual threads. O objetivo era claro, escalar aplicações com milhões de threads leves sem o custo elevado das threads tradicionais do sistema operacional.
- **#36 Records como JPA Entities fazem a aplicação nem subir:** Você tentou migrar suas entities JPA para records pensando em modernizar o código. A aplicação nem chega a iniciar.
- **#37 Imutabilidade não é estilo. É proteção de domínio.:** Value objects mutáveis (preço, desconto, total) causam bugs por estado compartilhado; prefira imutáveis / records.
- **#38 Por que John McClane calcularia o Natal errado com LocalDateTime (e você também):** Use ZonedDateTime/Instant para instantes; LocalDateTime não tem fuso. Duration = tempo físico; Period = calendário (getDays só a parte dias).
- **#39 Extends considerado perigoso, quando OO vira anti-pattern:** Um erro comum em OO é estender classes concretas para adicionar auditoria ou validação. Imagine um sistema em que todo pedido precisa passar por validação de crédito antes de ser persistido.
- **#40 Quase todo dev Java usa o relógio errado para medir execução.:** currentTimeMillis/Instant para calendário e logs; nanoTime() para elapsed/benchmark (monotônico).
- **#41 UUIDv4 foi uma boa ideia… até chegar no banco.:** UUID.randomUUID() fragmenta índices B-tree; prefira UUIDv7 ou ULID (time-ordered) em vez de IDs sequenciais previsíveis.
- **#42 Se sua classe não é final, você pode estar criando um bug invisível:** se a classe não foi desenhada para herança, proíba com final. Use composição, decorators ou wrappers para estender o comportamento. Eles são mais explícitos, mais testáveis e falham mais cedo. Herança exige disciplina extrema. Na dúvida, não permita.
- **#43 O antipadrão XServiceImpl e como substituí-lo por contratos úteis:** crie interfaces quando houver variação real no comportamento ou uma fronteira entre módulos. Mantenha-as pequenas, comportamentais e estáveis. Teste com múltiplas implementações antes de lançar.
- **#44 Template Method aplicado às interfaces:** se a interface puder ter comportamentos derivados por default method, use default method. Se ainda houver lógica repetida, estado comum ou alguma ordem fixa de execução, complete com uma classe abstrata que implemente a interface parcialmente.
- **#45 Testar private deveria ser proibido?:** Não torne nada public só para testar. Prefira extrair lógica ou usar package-private quando fizer sentido. Projetos encapsulados são mais testáveis e mais fáceis de evoluir porque deixam claro o que deve ser observado e o que é um detalhe interno.
- **#47 Java passa por valor ou por referência?:** Java sempre passa por valor. Ponto final.
- **#48 Enums em Payment e o antipadrão switch-on-type:** quando o enum começa a crescer mais rápido do que o entendimento do time, está na hora de evoluir para uma hierarquia. Segurança de tipo, legibilidade e evolução do código ganham com isso.
- **#49 Combine estado e comportamento para evitar modelos anêmicos:** se você precisa de getter para tomar uma decisão e de setter para aplicar o resultado, o comportamento provavelmente deveria estar na própria classe.
- **#50 Uma palavra esquecida pode causar vazamento de memória em Java: static:** Se a classe interna não precisar acessar campos ou métodos de instância da classe externa, declare-a static. Você economiza memória, reduz acoplamento e deixa a intenção explícita.
- **#51 Exceção não é regra de negócio:** Se o cenário for esperado, modele no retorno. Se for inesperado, lance uma exceção. Se você precisa de try-catch para definir a regra de negócio, o contrato da API provavelmente está errado.
- **#52 Por que Spring, Hibernate e JPA preferem unchecked exceptions?:** Se o chamador não pode fazer nada útil além de logar e propagar, então unchecked. Se a recuperação é esperada, checked pode fazer sentido, mas avalie primeiro Optional ou o tipo de retorno (pílula #51).
- **#53 "Invalid payload" é o novo NullPointerException:** Se getMessage() da sua exceção não permite reproduzir o cenário sem olhar o código-fonte, a mensagem está incompleta. Inclua sempre o que esperava, o que recebeu e de onde veio.
- **#54 Quando a exceção certa depende de uma decisão do time, não do compilador.:** Não importa se você escolhe NPE ou IAE para null proibido. Importa que o time escolha um, documente e nunca misture os dois no mesmo sistema.
- **#55 Exceção legítima não viaja sem causa.:** No @Service, toda exceção relançada encadeia o cause e usa .formatted() com o contexto da operação. No @RestControllerAdvice, ProblemDetail entrega um HTTP padronizado. O cliente recebe contexto. O log, o stack trace completo.
- **#56 Cast Sem Verificação Derruba Produção:** Cast sem instanceof antes é uma suposição disfarçada de código. Se o tipo vem de fora do seu controle (rede, driver, stream), valide antes, trate o inesperado e só então siga o fluxo.
- **#57 A IDE gerou um catch vazio. Você aceitou. Agora, o time não sabe se é um bug ou uma decisão:** todo catch vazio é culpado até que se prove o contrário. Use "ignored" e um comentário CONDIÇÃO -> EFEITO. Se não consegue explicar por que ignora, não ignore.
- **#58 Log and throw, o antipadrão que multiplica seu custo de observabilidade:** se você relança, não logue. Se você loga, não relance sem decisão explícita. Preserve a causa nas camadas internas e concentre o log de erro no ponto que define retry, fallback ou a resposta final.
- **#59 ConcurrentModificationException pode não ter nada de concorrência. Deixa eu explicar.:** No for-each, nunca modifique a coleção diretamente. Se precisar remover durante a iteração, use removeIf com um predicado puro ou Iterator.remove() explícito.
- **#60 Fail Fast - falhe cedo, falhe claro:** Falhe no topo do método, melhor ainda, no construtor do tipo. Reporte invariantes violadas (IllegalArgumentException) de forma distinta de falhas de recurso. Nunca misture os dois.
- **#62 e.getMessage() parece inofensivo. Parece.:** Ao relançar, passe a exceção original (, e), nunca só e.getMessage(); wrapping só se agregar tipo/contexto/contrato.
- **#63 Java 26 fala HTTP/3. Sem OkHttp, sem Apache, sem desculpa.:** Configure HTTP_3 no HttpClient do JDK 26 para consumir APIs externas com potencial de menor latência, especialmente em redes mais instáveis. O fallback para HTTP/2 é automático. No servidor, espere o suporte amadurecer.
- **#64 Em CompletableFuture, erro também é resultado. E isso muda tudo.:** Em fluxo assíncrono, defina o papel de cada etapa: exceptionally() recupera, handle() transforma, whenComplete() observa. Quando os papéis se misturam, log vira fallback e fallback vira log.
- **#65 InterruptedException não é um ruído. É um pedido de cancelamento cooperativo.:** nunca engula uma InterruptedException sem restaurar o flag. Chame Thread.currentThread().interrupt() e não siga como se nada tivesse acontecido.
- **#66 Checked exceptions em lambdas não desaparecem. Elas apenas mudam de lugar.:** em lambdas e streams, não esconda checked exceptions. Trate fora do pipeline ou traduza para unchecked, com o contexto e a causa preservados. Null não recupera falha, apenas disfarça o erro.
- **#67 quando o finally interrompe a propagação da exceção:** finally só para cleanup — nunca return/break/continue (engolem a exceção do try/catch).
- **#68 Quando o legado grita, o log não precisa repetir:** Limite stack (%ex{30}) e use DuplicateMessageFilter; dedupe na format string SLF4J, não em concatenação.
- **#69 O Elasticsearch removeu catch(Throwable). O Pulsar adicionou. Os dois estavam certos.:** Capture Exception na lógica de negócio. Reserve catch(Throwable) para boundaries de infraestrutura, como startup, thread pools e workers, onde registrar falhas graves antes de encerrar é responsabilidade do runtime.
- **#70 Result Pattern, quando o erro faz parte da resposta:** Se você está modelando o que o negócio pode responder, use Result. Se está modelando o que deu errado e você não esperava, use exceções.
- **#71 Nem toda exceção merece uma segunda chance:** Repita apenas as exceções transientes. Se o mesmo input sempre produz o mesmo erro, retry é desperdício disfarçado de resiliência.
- **#72 o bug silencioso entre sobrecarga e sobrescrita em equals:** equals(MyType) sobrecarrega — use @Override equals(Object); se equals, também hashCode.
- **#73 Quando o contains() mente, o contrato entre equals e hashCode:** se equals define identidade, hashCode precisa contar a mesma história. Se cada um contar uma, sua coleção vira um terreno minado. Em entidades JPA, evite @Data e use @EqualsAndHashCode(onlyExplicitlyIncluded = true) incluindo apenas um critério estável de identidade.
- **#74 o erro inofensivo no toString() que pode disparar SQL e travar seus logs:** toString sem caminhar grafo, sem SQL/lazy JPA e sem Locale; Lombok @ToString(onlyExplicitlyIncluded=true).
- **#75 você copiou o objeto ou apenas a referência?:** List.copyOf no construtor já resolve a entrada e a saída, porque o resultado é não modificável e o getter pode retornar o campo direto. Copiar de novo no getter só faz sentido se o campo interno for mutável, como new ArrayList<>(items).
- **#76 Comparable e Comparator: ordenação fluida sem armadilhas:** Toda classe de valor com ordem natural deve implementar Comparable. Em compareTo e compare, nunca subtraia inteiros nem use os operadores menor e maior. Prefira Integer.compare, Long.compare, Double.compare, ou Comparator.comparing com thenComparing.
- **#77 o cast que parece seguro, mas não é:** Use List<?> quando a lista é de um tipo desconhecido e você só precisa ler. Use List<T> quando o tipo importar e deva ser preservado. Use List<Object> apenas nos casos raros em que a coleção realmente precisa misturar tipos. E evite List raw, porque ele desativa parte da proteção que os generics trouxeram com a evolução do Java.
- **#78 Transforme suposição em checagem:** Antes de usar @SuppressWarnings("unchecked"), verifique se a própria JDK oferece uma forma de validar explicitamente o tipo. Class.asSubclass substitui o cast silencioso por uma checagem clara, falha cedo na fronteira correta e preserva a informação de tipo.
- **#79 Listas rápidas para testes melhores.:** List.of para fixtures imutáveis; se o SUT muta a lista, new ArrayList<>(List.of(...)); evite double-brace.
- **#80 Datafaker e Instancio, massa de teste com realismo e estrutura.:** Use Datafaker (não JavaFaker abandonado) com seed explícito; combine com Instancio para grafos aninhados.
- **#81 PECS, Producer Extends Consumer Super:** Em parâmetros de método, aplique PECS. Se a coleção produz valores que você lê, use List<? extends T>. Se consome valores que você adiciona, use List<? super T>. Se faz os dois, parametrize o método com <T>.
- **#82 ParameterizedTypeReference, quando .class não basta:** Para tipos parametrizados em respostas REST, .class não basta. Use ParameterizedTypeReference, o super type token do Spring para RestTemplate e WebClient. List.class devolve um LinkedHashMap e ocorre um ClassCastException no primeiro get.
- **#83 CAP#1, o erro estranho dos wildcards:** Quando CAP#1 aparecer, pergunte: leitura e escrita pertencem à mesma captura? Se sim, use um helper privado com <T>. Se vêm de wildcards diferentes, o compilador está certo em bloquear.
- **#84 EnumSet é a escolha natural para modelar permissões em Java:** Use EnumSet quando o conjunto contiver apenas constantes de um mesmo enum. Ele é mais rápido e mais enxuto do que HashSet, mas é mutável. Faça cópia defensiva e nunca insira null.
- **#85 Máquinas de estado em Java com EnumMap sem if espalhado:** Use EnumMap<Status, EnumSet<Status>> para responder "de X posso ir para Y?". Mapeie os estados finais com EnumSet.noneOf, valide com contains e mantenha o grafo centralizado.
- **#86 Parametrize a chave, não o container:** Quando precisar guardar valores de tipos diferentes no mesmo container, parametrize a chave, não o container. Use Class<T> como chave e type.cast() na leitura. Cast manual sobre Map<String, Object> indica que falta um Typesafe Heterogeneous Container.
- **#87 Enums não são extensíveis, mas o design pode ser:** não tente tornar o enum extensível. Modele o contrato com uma interface, implemente o enum e escreva suas APIs contra essa interface. Assim, outros enums ou tipos podem participar do mesmo modelo sem quebrar o fechamento do enum.
- **#88 Auditoria de regra de negócio com marker annotation e Spring AOP.:** Auditoria transversal: annotation marcadora + Aspect (@annotation); não misture com regra de negócio nem com Envers/Micrometer.
- **#89 desserialização não é parsing:** Não desserialize dados não confiáveis com serialização nativa. Prefira schema, como Protobuf. Se for inevitável, use allowlist, transient e valide em readObject.
- **#90 Criptografia não é lugar para criatividade:** precisa ler depois? AEAD. Só precisa detectar adulteração? MAC ou assinatura. É a senha do usuário? Hash adaptativo, como bcrypt. Nunca plain text, nunca cripto caseira.
- **#91 Sua lambda cabe em uma linha? Se não cabe, ela não deveria ser uma lambda:** Lambda boa tende a ser curta, local e autoexplicativa. Se precisar de nome, documentação ou várias linhas para ser entendida, extraia para um método e use method reference. Classes anônimas, só em casos específicos.
- **#92 Predicate não é um if com roupa nova:** use Predicate para critérios booleanos pequenos, nomeados e sem efeitos colaterais. Quando precisar transformar dados, alterar estado, explicar a falha, registrar ações ou executar I/O, escolha outra abstração.
- **#93 Quando uma lambda merece virar method reference:** Pergunte se a lambda faz algo além de chamar um método existente com os parâmetros recebidos, na mesma ordem. Se não fizer, cabe usar method reference, desde que a leitura fique realmente mais clara.
- **#94 Function<Integer, Integer>: a lambda parece simples, mas o boxing está escondido:** Se uma operação numérica recebe e devolve int, long ou double, procure a interface primitiva correspondente. Em caminhos muito executados, preserve os primitivos desde a fonte e use profiling antes de otimizar.
- **#95 Sua interface funcional própria precisa justificar a existência:** antes de escrever @FunctionalInterface, procure a equivalente em java.util.function. Só crie a sua se ganhar nome de domínio em uma API muito usada, um contrato forte ou métodos default próprios. Renomear Predicate não é ganho de expressividade, é perda de interoperabilidade.
- **#96 variável guarda valor, Supplier guarda comportamento:** use Supplier quando quiser passar como produzir um valor, não o valor pronto. Use Consumer quando quiser passar o que fazer com um valor, sem esperar retorno.
- **#97 Aquele em que o loop vence o stream:** Stream para transformar, filtrar, agrupar, reduzir e buscar. Loop para alterar uma variável local, encerrar o método com return e propagar a exceção checada. Refatore um no outro quando a leitura melhorar, não por padrão.
- **#98 Filter escolhe, map transforma:** Todo pipeline tem três partes, e entender essa divisão resolve boa parte da confusão inicial. Existe uma fonte, que quase sempre é uma coleção, existem as operações intermediárias, que descrevem o que você quer fazer, e existe uma operação terminal, que fecha o pipeline e devolve o resultado.
- **#99 Como um stream volta a ser uma lista:** O forEach devolve void, então nunca retorna um resultado. Se você criou a coleção antes do pipeline para preenchê-la dentro dele, troque por uma operação terminal que devolva um valor e deixe que ela monte a coleção.
- **#100 Agrupar sem for aninhado:** Se você criou um Map antes do loop para depois preenchê-lo grupo por grupo, esse trabalho é do groupingBy. A função que você passa define a chave, e o uso de counting substitui a lista de elementos pela quantidade deles.
- **#101 Ordenar e trazer os n primeiros:** Prefira limit a recortar a lista depois de ordenar. Ele nunca estoura quando há menos itens do que o pedido e devolve uma lista independente. Com sorted antes, lembre que a ordenação ainda percorre tudo.
- **#102 Quando map não basta:** Se a função que você passaria ao map retorna uma coleção e você quer os itens dela, use flatMap. O map devolve uma lista de listas; o flatMap devolve uma lista única, pronta para filter, sorted e o restante da pipeline.
- **#103 Quando o pipeline precisa lembrar (agora nem tão):** Se a operação depende do que veio antes, como lotes, janelas ou totais acumulados, procure primeiro na classe Gatherers. O windowFixed já entrega o último lote incompleto, justamente o que o loop manual costuma esquecer.
